# prefix caching 절감 실측 (M5 Pro, vLLM Metal)

[English](cache-savings-m5.md)

측정일 2026-09-24, 공개 이력 이전의 personaload 빌드, AIPerf 0.12.0.

## 요약

- 캐릭터챗 워크로드에서 서빙 엔진의 prefix caching을 켜면, 같은 SLO 안에서 출력 토큰당 비용($/1M out)이 **47~73%** 줄었다(Qwen3 0.6B~4B).
- 8B와 14B는 캐시 없이는 가장 낮은 동시성에서도 SLO를 지키지 못했다. SLO를 무시한 최대 처리량으로 비교해도 56~66% 이상 차이가 난다.
- 페르소나가 500개로 제각각이어도 절감률은 **38~53%**였다(0.6B~4B). 첫 턴은 거의 캐시에 안 맞지만, 둘째 턴부터 같은 세션의 히스토리가 캐시에 맞는다([페르소나 500개](#페르소나-500개-persona-diverse-조건) 절).
- 절감은 모두 입력 처리(prefill) 쪽이다. 요청당 출력 토큰 수는 캐시와 무관하게 같았다. 출력 토큰당 비용이 줄어든 것은, prefill에서 아낀 GPU 시간이 더 많은 출력 생성에 쓰였기 때문이다.
- 이 수치는 Apple Silicon에서 잰 것이다. NVIDIA 서버 GPU에서는 prefill이 상대적으로 싸서 절감률이 더 작을 가능성이 크다. 실제 서버 수치는 대상 GPU에서 같은 쌍을 돌려서 얻는다([재현](#재현) 절).

## 용어

- **SLO (Service Level Objective, 서비스 수준 목표)**: 사용자가 겪는 품질을 숫자로 정한 목표다. personaload는 단계마다 세 조건을 판정한다.
  - `TTFT p95 ≤ slo.ttft_p95`: 요청의 95%가 이 시간 안에 첫 토큰을 받는다. 사용자가 "답이 시작되기까지" 기다리는 시간이다.
  - `ITL p95 ≤ slo.itl_p95`: 스트리밍 청크 사이 간격의 95%가 이 안에 든다. 답이 "써지는 속도"다. 100 ms면 초당 약 10토큰 이상이다.
  - `에러율 ≤ slo.error_rate_max`
  - 셋 중 하나라도 어기면 FAIL이다.
- **왜 SLO 기준으로 비용을 보나**: 동시성을 올리면 처리량(tok/s)은 계속 늘지만 사용자는 점점 오래 기다린다. 그래서 "같은 사용자 경험을 지키면서 얼마나 싸게 처리하나"로 비교해야 공정하다. personaload 헤드라인은 SLO를 통과한 단계 중 처리량이 가장 높은 단계의 $/1M out이다.
- 이 실험의 SLO는 TTFT p95 2초, ITL p95 100 ms, 에러율 1%다.

## 환경

| 항목 | 값 |
|---|---|
| 장비 | MacBook Pro, Apple M5 Pro, 48 GB 통합 메모리 |
| 엔진 | vLLM 0.30.0 + [vllm-metal](https://github.com/vllm-project/vllm-metal) 0.30.0 (Homebrew) |
| 모델 | `mlx-community/Qwen3-{0.6B,1.7B,4B,8B,14B}-4bit` |
| 공통 서버 플래그 | `--served-model-name local-model --max-model-len 8192 --enable-prompt-tokens-details` |
| 캐시 켬 / 끔 | `--enable-prefix-caching` / `--no-enable-prefix-caching` |

- 모델마다 캐시를 켠 서버와 끈 서버에 **같은 데이터셋**을 돌렸다. 시드가 같아 단계별 `dataset.jsonl` sha256이 같다.
- 노트북 발열 효과를 줄이려고 모델마다 켬·끔 순서를 번갈아 바꿨다(0.6B·4B·14B는 켬 먼저, 1.7B·8B는 끔 먼저).

## 워크로드

```yaml
name: sweep
seed: 3
target:
  base_url: http://127.0.0.1:8000/v1
  model: local-model
  timeout: 60s
  max_tokens_field: max_tokens
  extra_body: {chat_template_kwargs: {enable_thinking: false}}
personas:
  count: 5
  system_prompt_tokens: {min: 1500, max: 3000}
session:
  turns: {min: 4, max: 10}
  user_input_tokens: {dist: lognormal, mean: 40, stddev: 20, min: 5, max: 150}
  max_output_tokens: {min: 32, max: 96}
  think_time: {dist: exponential, mean: 2s, min: 500ms, max: 8s}
  persona_selection: zipf
  zipf_s: 1.1
load:
  mode: concurrency
  stages:
    - {concurrency: 2, duration: 30s, warmup: 10s}
    - {concurrency: 4, duration: 30s, warmup: 10s}
    - {concurrency: 8, duration: 30s, warmup: 10s}
    - {concurrency: 16, duration: 30s, warmup: 10s}
slo:
  ttft_p95: 2s
  itl_p95: 100ms
  error_rate_max: 0.01
cost:
  gpu_hourly_usd: 1.0   # 시간당 $1 기준: 실제 장비 단가를 곱하면 된다
```

- 페르소나 5개가 긴 system 프롬프트를 공유하고, 멀티턴 히스토리가 쌓이는 캐릭터챗 형태다.
- 출력이 짧아(32~96토큰) 입력 비중이 큰 워크로드다.
- Qwen3 thinking은 껐다. 켜 두면 짧은 `max_tokens`를 추론에 다 써 버린다. smoke.yaml에서는 응답 48/48이 상한에서 끊겼다.

## 해석

- **절감은 prefill에서 나온다.** 캐시가 하는 일은 이미 계산한 입력 앞부분(prefix)의 계산을 건너뛰는 것이다. 그래서 TTFT가 3~12배 줄었고, 남은 계산 여유만큼 같은 SLO에서 동시성을 더 받을 수 있었다.
- **출력 토큰 수는 그대로다.** 요청당 출력 토큰 평균은 캐시를 켜도 꺼도 57~61개로 같았다(0.6B 59.6 vs 57.0, 4B 61.5 vs 58.9, 14B 58.1 vs 59.2).
  - 출력 토큰은 한 개씩 생성해야 하므로 prefix caching으로 건너뛸 수 없다.
  - 그래도 **출력 토큰당 비용**은 줄었다. 비용 = GPU 시간 ÷ 출력 토큰 수인데, 분모는 그대로이고 prefill로 쓰던 GPU 시간이 줄었기 때문이다.
  - 동시성이 낮을 때는 ITL(생성 속도)이 켬·끔 모두 같았다(0.6B 7.2 vs 7.0 ms). 동시성이 높을 때는 캐시를 켠 쪽이 약간 빨랐다(0.6B 동시성 16: 26.1 vs 37.4 ms). prefill 작업이 줄어 생성 단계를 덜 방해했기 때문이다.
- **출력 쪽을 줄이는 수단은 따로다.** 이번 측정의 대상이 아니다.
  - 출력 토큰 수를 줄이는 방법: thinking 끄기(smoke.yaml에서 상한까지 쓴 응답 48/48 → 30/55), `max_tokens` 제한.
  - 출력 토큰 생성 자체를 싸게 하는 방법: 양자화(FP8 등), speculative decoding, 엔진·GPU 교체. personaload로 같은 시나리오를 돌려 비교할 수 있다.
- **hit가 어디서 오나.** 새 세션의 첫 턴은 87.7%였다. 이건 페르소나 공유 덕분이다. 이후 턴은 94.3%로, 같은 세션의 히스토리 재사용이 더해진다. 페르소나가 제각각이면 첫 턴 hit가 1.5%로 떨어지고 이후 턴은 95.3%로 유지된다([페르소나 500개](#페르소나-500개-persona-diverse-조건) 절).
- **모델이 클수록 절감이 크다.** prefill 계산량은 대략 파라미터 수 × 입력 토큰 수에 비례한다. 그래서 큰 모델일수록 캐시가 건너뛰는 계산의 비중이 커진다.

- 8B와 14B의 캐시 끔 쪽은 SLO를 무시한 최대 처리량으로 계산한 하한이다. 페르소나 500개일 때 8B는 17.2 tok/s($16.15/1M), 14B는 10.8 tok/s($25.72/1M)였다. 조건마다 끔 쪽 처리량이 달라서, 두 조건의 하한끼리는 비교하지 않는다.

**해석**

- **첫 턴만 캐시를 잃는다.** 첫 턴 cache hit는 87.7%에서 1.5%로 떨어졌다(요청 217건). 둘째 턴부터는 95.3%였다(요청 790건). 같은 세션의 히스토리 재사용만으로도 비용이 절반 안팎 줄었다.
- **페르소나 공유는 캐시가 있을 때만 돈이 된다.**
  - 캐시 켬: 페르소나 500개가 5개보다 7~76% 비쌌다(4B는 $2.491 대 $4.386).
  - 캐시 끔: 두 조건의 비용이 거의 같았다(4B는 둘 다 $9.395, 0.6B만 16% 차이). 캐시가 없으면 공유해도 계산이 줄지 않는다.
- **큰 모델은 캐시를 켜도 동시성 16에서 무너졌다.** 8B는 13.2 tok/s(페르소나 5개일 때 94.0), 14B는 동시성 8에서 15.0, 16에서 0이었다.
  - 메모리 부족은 아니었다. vLLM 로그상 KV 캐시 사용률은 12~18%였고, 선점(preemption)은 0건이었다.
  - 첫 턴 입력 처리가 GPU를 차지했다. 같은 구간 vLLM 로그에서 입력 처리는 초당 400~1,000토큰인데 출력 생성은 초당 2~5토큰(한 구간 48)이었다. 새 세션마다 캐시에 없는 약 2,000토큰 페르소나를 처리했기 때문이다. 페르소나 5개일 때는 같은 구간이 입력 80~210, 출력 85~96토큰/초였다.
  - 그래서 페르소나가 다양한 서비스에서는 페르소나 프롬프트 길이가 비용과 처리 한계에 직접 영향을 준다.

## 한계

- **서버 GPU와 다르다.** Apple Silicon + MLX 4bit 결과다. H100·L40S 같은 서버 GPU는 메모리 대역폭 대비 연산 성능이 훨씬 높아 prefill이 상대적으로 싸므로, 절감률은 더 작을 가능성이 크다.
- **각 조건을 한 번씩만 쟀다.** 발열·배경 부하 변동을 반복 측정으로 줄이지 않았다.
- **두 스윕은 시드가 같다.** 페르소나 5개와 500개 조건은 세션 모양(턴 수, 출력 상한)이 같고 페르소나 텍스트만 다르다. 그래서 두 조건의 차이는 페르소나 공유 여부에서 온다.
- **동시성 단계가 성기다.** 2/4/8/16이라 헤드라인 절감률이 거칠다. 특히 SLO 경계가 단계 사이에 있으면 과장될 수 있다.
- **출력이 짧다.** 32~96토큰이라 입력 비중이 큰 워크로드다. 출력이 길면 절감률이 줄어든다.

## 재현

```bash
# 엔진 (Apple Silicon)
brew tap vllm-project/vllm-metal https://github.com/vllm-project/vllm-metal
brew install vllm-project/vllm-metal/vllm-metal

# 모델마다: 캐시 켬
vllm serve mlx-community/Qwen3-8B-4bit --host 127.0.0.1 --port 8000 --served-model-name local-model \
  --max-model-len 8192 --enable-prefix-caching --enable-prompt-tokens-details
personaload run sweep.yaml --out runs/8B/on

# 캐시 끔 (서버를 다시 띄운다)
vllm serve mlx-community/Qwen3-8B-4bit --host 127.0.0.1 --port 8000 --served-model-name local-model \
  --max-model-len 8192 --no-enable-prefix-caching --enable-prompt-tokens-details
personaload run sweep.yaml --out runs/8B/off

# 비교
personaload report runs/8B/on/* runs/8B/off/*
```

NVIDIA 서버에서는 `scripts/vllm-linux.sh`로 띄운 서버와, 같은 명령에 `--no-enable-prefix-caching`을 준 서버를 비교하면 된다.
